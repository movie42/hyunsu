Agent Control 기록\
Agent Control 관련 세션 기록 175개를 전부 읽었습니다. 프로젝트 본체, Orca 워크트리, 테스트용 scratchpad 세션까지 포함했고, 기간은 11/2 밤부터 11/19까지 18일입니다. 그사이 커밋은 68개, TS 코드는 약 5.2만 줄, flow 작업 문서는 32개가 쌓였습니다. 글감은 주제별로 묶었고, 괄호 안 날짜는 해당 세션의 날짜입니다.

**1. 출발과 방향 전환**

* **출발점 (11/2 23:35)**: Orca로 에이전트를 여러 개 열어두니 내가 이어서 할 일과 진행도를 한눈에 볼 수 없었습니다. 산출물 HTML 하나 여는 데도 클릭이 두 번 들었습니다. "일단 프로토타입 구현 후에 flow로 문서만 써줘"로 시작했고, 그날 밤 바로 "데스크톱 앱으로 말아서 Dock에 등록"까지 갔습니다.
* **만들다 보니 Orca를 다시 만들고 있었다**: 세션도 여기서 열고 싶다고 하면서 스스로 "이거 뭐... 오르카네...."라고 했습니다. 이후 18일은 Orca 의존을 하나씩 걷어내는 과정이었습니다. 세션 열기, 터미널, git 그래프, 파일 탐색, 워크트리 생성 순으로 들어왔습니다.
* **Herder로 갈아탈까 고민한 날 (11/4)**: "orca가 계속 열려있는 것도 짜치는데…"라고 했다가 그냥 Orca를 쓰기로 했습니다. 원래 원했던 건 "orca 화면을 통째로 보는 게 아니라, 대화 중인 에이전트 진행 상태를 GUI처럼 보는 것"이었다고 정리되는 대목입니다.
* **회사와 집의 워크플로가 다르다**: 회사에는 기획서가 있어서 구현 질문만 받으면 됩니다. 집에서 혼자 할 때는 PRD부터 써야 합니다. 그래서 단계 정의가 둘로 갈렸습니다.

**2. "상태"라는 단어와의 싸움**

* **"완료"인데 끝난 게 아니었다**: 내 턴이 왔을 뿐인데 화면에는 "완료"로 떴습니다. 그래서 상태 이름을 내 차례 / 작업중 / 쉬는중으로 바꿨습니다.
* **휴면 → "잠자는 중"**: 멈춘 세션이나 오래된 세션을 따로 표시하려고 이름을 고르다가 이렇게 정했습니다 (11/17).
* **"멈추기 눌러도 상태가 안 바뀐다"가 여러 번 재발**: 빌드 전에는 되다가 빌드 후에 다시 안 됐습니다. 추적이 까다로웠던 버그로 쓸 수 있습니다.
* **결국 사람이 상태를 정하게 했다 (11/18)**: 여러 세션을 골라 우클릭 한 번으로 쉬는중·잠자는 중으로 바꾸게 했습니다. 자동 판정의 한계를 인정한 이야기입니다.
* **할일 칸반의 워크플로 오해**: "워크플로우는 말 그대로 플로우야… 진입과 끝만 알면 상태는 그때그때 보고 정할 수 있잖아. Jira는 AI가 잘만 옮겨주던데." 에이전트가 상태 기계에 집착했고, 사용자는 흐름을 원했습니다.

**3. 에이전트의 대화를 어떻게 훔쳐보나 (기술 글감)**

* **Orca도 결국 터미널일 뿐인데 대화를 어떻게 가져오나**: 이 질문에서 세션 기록 파일을 직접 읽는 구조가 나왔습니다. 이어서 "그럼 이 기능 때문에 토큰을 더 쓰나?"라는 질문도 있었습니다.
* **헤드리스 모드가 아니면 대화를 못 가져온다**: 같은 문제가 `/resume`이나 `/clear` 같은 대화형 명령에서도 나왔습니다. 터미널에서 시작한 세션을 UI로 가져오면 아무것도 안 보였습니다 (11/16, 11/18).
* **권한 요청과 선택지를 hook 기반 구조화 데이터로 받기 (11/3)**: `bun run hook:install`로 Claude Code 설정에 권한 hook을 설치하고, `127.0.0.1:3199`로 받게 했습니다. 중간에 "기본 실행이 dangerous permission 모드 아니야?"라는 질문도 나왔습니다.
* **localhost가 엉뚱한 곳에 붙는 문제**: 다른 프로젝트의 dev 서버를 잡는 일이 있었습니다. 포트 충돌을 해결한 이야기입니다.

**4. 에이전트가 에이전트 앱을 테스트한 흔적**

이 묶음은 재미 요소로 쓰기 좋습니다.

* 기록에 이상한 테스트 세션이 남아 있습니다.
  * "AskUserQuestion으로 색 하나 고르게 해줘"
  * "Run exactly this bash command: touch .next/cache/probe-touch.txt"
  * "1부터 400까지 세어줘. 도구는 쓰지 마." (멈춤 테스트)
  * "강에 대한 3000단어 에세이" (ESC 테스트)
  * "1+1은? 숫자만 답해." (일꾼 세션 e2e)
* "지금 헤드리스 버튼 눌렀고 너에게 메시지가 가면 성공이야": 기능 검증을 대화 자체로 했습니다.
* 지휘자가 일꾼에게 일을 맡기고 보고를 받는 e2e 로그가 실제로 남아 있습니다. "\[Agent Control] 세션 repo-a의 보고: # e2e" 같은 줄입니다.

**5. 의도 diff: 가장 독창적인 기능 (11/4\~)**

* **동기**: "너가 엄청 많은 양의 코드를 수정하는데 그 의도를 일일이 파악하기 너무 힘들어서, 의도대로 읽을 수 있게 정렬해주는 diff가 필요해." AI 시대의 코드 리뷰 문제를 정면으로 다루는 대목이라 글의 중심으로 삼기 좋습니다.
* **기준을 분명히 함**: 작업 계획서와 묶되 flow 스킬과 합치지는 말 것.
* **"의도 미상"이 너무 많았다**: 그래서 import 의존성 트리와 기능 단위 묶음을 요구했습니다.
* **diff의 한 줄을 눌러 그 코드를 쓴 세션에게 직접 물어보는 기능**: 실제 질문으로 "let은 왜 이렇게 많이 쓴 거야, 안전성이 떨어져", "resolveRange 너무 복잡한데 설계가?"가 남아 있습니다.
* **저장 위치 논쟁**: "앱 재시작하면 사라진다고? 안 되는데;;"와 "프로젝트 안에 파일 하나 더 늘어나는 건 싫다" 사이에서 저장 위치를 정했습니다.
* **디테일**: Cursor 테마를 Shiki로 이식했고, 클릭과 드래그를 구분하지 못하던 버그를 고쳤습니다.

**6. 실패담: 계획을 쪼갰더니 핵심이 빠졌다 (11/16)**

가장 강력한 에피소드입니다.

* **무슨 일이 있었나**: "프로젝트 전체 보기 + 지휘자"를 원했는데, 계획이 project-overview와 session-orchestration 두 개로 쪼개졌습니다. 그 사이에서 그래프 화면이 빠졌습니다.
* **사용자의 반응**: "내가 너 이럴 줄 알았다... 계획 분리하더니 결국 내가 원하는 대로 구현이 안 됐어... 어쩔 거야??"
* **복구 과정**: 현재 세션을 handoff 문서로 넘기고, 새 세션에서 두 계획을 비교해 잘못된 점을 보고받고, 하나로 합쳐 재구현했습니다.
* **교훈이 규칙이 됐다**: 이 일이 "기능을 화면과 분리하지 말 것"이라는 메모리로 남았습니다.
* **비슷한 오해 하나 더**: 지휘자 기능이 앱 전체 단위로 붙었을 때 "내가 언제 그렇게 넣어달라고 했어? 플젝 단위로 해달라고 했잖아"라는 반응이 있었습니다.

**7. 병렬 에이전트끼리 서로 덮어쓰기**

* "파일 탐색 기능이 이전에 수정했던 거 덮어쓴 것 같은데... 기능이 있다 사라졌다 난리냐?"
* "우클릭 메뉴 커밋(5517201)은 있는데 왜 기능이 안 보이냐"
* 이후 지시가 바뀌었습니다: "두 작업 다 끝나면 한 번에 빌드해줘, 서로 묻히지 않게", "최신 동작으로, 서로 수정한 거 덮어쓰기 하지 말고". 멀티 에이전트로 병렬 개발할 때의 현실을 보여주는 장면입니다.

**8. 캔버스와 지휘자**

* **그래프에서 캔버스로**: 처음 받은 그래프 시안에 "방향이 완전히 다르네 ㅋㅋ"라고 했고, archify 스타일 그래프를 보여주며 다시 요청했습니다. 그다음엔 "디자인 너무 구린데"를 거쳐 "기본 화면 자체가 피그마 같은 캔버스여야 해, 그룹으로도 묶을 수 있게"로 갔습니다.
* **지휘자 세션 구조**: 지휘자가 `start_session` 같은 MCP 도구로 일꾼 세션을 열고, 일꾼이 끝나면 보고가 지휘자에게 돌아옵니다. 범위는 프로젝트 단위에서 시작해 앱 단위로 넓어졌고, 다른 프로젝트의 워크트리까지 제어하게 됐습니다.
* **다른 프로젝트로 가는 연결선을 "대항해시대 항로"처럼**: 먼 곳의 항로를 보여주는 듯한 UI를 요청했고, 이어 "라인이 난잡해지지 않게"를 다듬었습니다.
* **템플릿 흐름의 실제 로그 (11/17)**: 계획 → 구현 → 검증 → 리뷰 → PR 초안 카드가 앞 카드의 답을 다음 카드로 넘깁니다. 작업 설명 자리에 브랜치 이름 `main`이 들어가는 버그가 있었는데, 이걸 다음 카드의 에이전트가 먼저 알아채고 "계획이 없어요, 작업 내용이 main 한 단어뿐"이라고 보고했습니다. 바로 인용할 수 있는 장면입니다.

**9. UI 취향 조율기**

* **포커스 기능**: chip 방식은 "전체 디자인이랑 안 어울린다", 체크박스는 "check가 좀 짜친다"라는 반응이었습니다. 다섯 번을 고쳤는데도 만족하지 못했습니다.
* **하위 워크트리 계층 표현**: "Orca가 하는 방식을 그대로 가져와서 그런 것 같은데"라는 지적에서 출발했습니다. 사용자가 직접 "sticky로 누적 + 하위 표현 둘 다"를 제안했고, 반응은 "훨씬 좋다. 굳!"이었습니다.
* **아이콘 일관성이 전역 규칙이 됐다 (11/13)**: "같은 기능의 아이콘은 동일하게 표현해야 한다고 하네스에 명시해줘." 이 요청이 지금 `~/AGENTS.md`의 "One Action, One Icon" 규칙입니다. 피드백이 규칙으로 굳는 과정의 좋은 사례입니다.
* **목록 순서는 고정**: "왜 에이전트 응답 순서에 따라 워크트리가 왔다 갔다 바뀌니? 고정이라고 이야기하지 않았니?" 결국 연 순서대로 고정하고, 순서는 드래그로 바꾸게 했습니다.
* **자잘한 결정들**: 아이콘은 벤또 하나만 남겼고, 드래그 핸들은 석삼(≡)으로 바꿨으며, 드래그를 시작하면 화면을 드래그 전용 모드로 전환하게 했습니다.
* **원격 확인 기능은 삭제했다가 git 그래프로 부활**: "차라리 만들 거면 git lens처럼 graph로" → 삭제 → 나중에 브랜치 전환까지 되는 git 그래프로 돌아왔습니다.

**10. 할일 칸반 (11/6\~)**

* **"내가 원한 건 대화형인데"**: 일괄 작성 기능이 나오자 이렇게 반응했습니다.

**11. 매일 반복된 운영 문제**

* **"빌드한 거야? 앱에 반영된 거야?"가 수십 번 나옵니다**: Dock 앱은 다시 빌드해야 반영된다는 사실을 결국 메모리에 저장했습니다.
* **데몬 재시작의 딜레마**: 재시작하면 지금 돌고 있는 세션이 전부 끊깁니다. 검증 카드의 에이전트가 직접 "재시작할지는 판단해 주세요"라고 넘기기도 했습니다.
* **말과 행동이 다르다**: "셸은 열어서 빌드는 하는데 재시작은 안 하는데? 메시지랑 동작이 다르잖아."
* **토큰과 사용량**
  * 사용량을 너무 자주 조회해서 429가 났고, 조회 간격을 늘렸습니다. Jira 조회는 5시간 간격으로 정했습니다.
  * 세션이 시작부터 컨텍스트를 7%나 먹는다는 걸 발견하고, 효과 큰 순서대로 줄였습니다.
  * 단순한 작업은 Haiku로 돌리자는 논의도 있었습니다.
* **알림의 변천사**: 앱 안 알림은 "전혀 쓸모없어"였습니다. macOS 네이티브 알림으로 바꿨고, 앱을 번들 ID로 다시 서명해서 알림 거부 문제를 풀었습니다 (최신 커밋). 지금은 알림을 닫을 수 없는 버그가 남아 있습니다.

**12. 기타 짧은 에피소드**

* **워크트리 생성 스킬의 소유권**: "dotfiles에 있으면 안 되고, 워크트리 생성은 Agent Control의 기능이니까 이 프로젝트가 스킬을 들고 있다가 설치해야 한다." 이 결정으로 `ac-worktree` 스킬이 생겼습니다.
* **flow 문서 패널**: 브라우저로 넘어가는 대신 앱 안에서 반반 분할로 열고, 탭을 OS로 드래그하면 별도 창이 됩니다. 질문에 답하면 문서를 만든 세션에 "질문에 답했어요"가 자동으로 전송됩니다.
* **브랜치가 바뀌면 flow 문서가 사라졌다**: "관제가 안 되잖아." 반대로 정리 안 된 워크트리의 문서는 계속 떠 있는 문제도 있었습니다.
